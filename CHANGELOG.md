- REQ-208 (FAIL-970 to FAIL-979): lessons for the launch courses can be pre-generated ahead of learners, under a hard budget, from GitHub Actions. A new manual workflow, "Pre-generate lessons" (`.github/workflows/pregenerate.yml`), runs estimate, submit and collect against production with `PROD_DATABASE_URL` and a separate `ANTHROPIC_PREGEN_API_KEY` (a key from a dedicated Console workspace with its own spend limit; the app's key is never used); it stops if either secret is missing, logs counts, the estimate and batch ids only, and uploads a counts-only summary. `--tracks` is a priority order (launch set: DPT, PTPREREQ, CCRNADULT, AWSSAA, AWSMLA, SECPLUS, CNA) and `--max-usd` (default 110) is checked against an upper bound -- every request at its full output size with the Batches discount, plus the live fact-check -- filling whole units in order and stopping at the first that does not fit, so the last track loses its later units; the estimate shows per-track counts, cost and the cutoff. The whole launch set on the batch-10 seed is 845 lessons, an upper bound of $100.23. The script now follows the app's lesson pipeline: two batches so the practice questions are written from the teaching text, the verification program requested and queued for Python/JavaScript/academic courses, the app's own fact-check, holdback and answer-shuffle steps, retired, hidden and authored objectives left out, and saving that never replaces an existing, voided or corrected lesson. Spend is recorded in `ai_calls` as purpose `pregen` (and `pregen_fact_check`) and, because a $50 run would otherwise pause chat and regenerate for learners, is left out of the `AI_GLOBAL_DAILY_CEILING_USD` sum. `--dry-run` builds every request and sends nothing. Runbook: "Pre-generating lessons". Owner action: create the Console workspace "pregen" with a $110 limit and add its key as `ANTHROPIC_PREGEN_API_KEY` in the `production-database` environment. No migration.

No migration. A hook, `setGlobalCeilingCheck`, is where the planned global daily AI ceiling plugs in. Learners at their limit see a plain message and everything that doesn't use the AI keeps working.

The app shows the confirm-it's-you prompt on the authenticator, connect-Google and delete-account screens (a Google sign-in button where the account has no password or code). No migration. - REQ-176: over-the-air updates from GitHub. A new workflow, "EAS update (OTA)" (`.github/workflows/eas-update.yml`), runs from the Actions tab (or a push to `ops/eas-update`) with a channel (default `production`), a message and `dry_run` (default on). It runs Expo doctor, works out this commit's Android and iOS runtime fingerprints, lists the finished EAS builds and recent updates, and says in the job summary, per platform, whether any build on that channel has the same runtime -- only those builds can take an update. Decision logic and tests in `.github/scripts/eas-ota.mjs`.

- REQ-200: a free, encrypted nightly database backup. The new "Nightly database backup" GitHub workflow (`.github/workflows/db-backup.yml`, daily at 11:23 UTC and on demand) streams `pg_dump --format=custom --no-owner --no-privileges` of the whole production database (Postgres 17 client) through `age` to the public key in `BACKUP_AGE_RECIPIENT`, so the plaintext dump never touches disk, and uploads the `.age` file with `manifest.json.age` (size, sha256, server version, table count, row counts of app_users/attempts/mastery; no user data), the same manifest encrypted to the same key, and `checksums.json` (a format number and the sha256 of the two `.age` files; the only plaintext, so the public artifact reveals no counts, table names or versions, and the workflow log prints none either) as an artifact kept 30 days. It connects with the existing `PROD_DATABASE_URL` secret in the `production-database` environment, refuses to run without it or the recipient (or with a private key pasted as the recipient), never prints the connection string, and fails if the backup is under 1 MB. `backend/scripts/restore-drill.sh` checks a downloaded backup's sha256 values, decrypts the manifest in memory with the same key, decrypts the dump into a fresh local database (after `scripts/ci/supabase-roles.sql`), checks the table and row counts against the manifest exactly and runs `migrate --status`. A new CI job ("backup-drill", `scripts/ci/backup-drill-test.sh`) runs dump -> encrypt -> decrypt -> restore -> verify with a throwaway key and database on every pull request. One-time setup, restore steps, limits (no point-in-time recovery, up to 24 h of loss) and when to move to Supabase Pro: docs/operations-runbook.md "Backups". No migration; nothing runs until `BACKUP_AGE_RECIPIENT` is set.
