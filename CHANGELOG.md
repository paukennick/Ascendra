- REQ-037: Added `subject_tracks.content_format` (migration `015_content_format.sql`), decoupled from `track_type`. `track_type` (graduate, certification, academic, professional, skills) has been doing two jobs -- pedigree/audience, and delivery format -- and every one of the 27 live tracks is the same shape underneath (units, objectives, mastery grading, PBQ, chat), so the mismatch hasn't hurt yet. With more AWS/Azure/nursing catalog expansion and new learning types (practice-exam-only tracks, flashcard decks, short readings) coming soon, that would have meant retrofitting `track_type` against live rows instead of adding a column ahead of need. `content_format` has one value today (`full_course`, matching every existing row); `POST /api/courses` accepts an optional `contentFormat`, validated and defaulting to `full_course`. - REQ-036: Home screen now groups courses by education category instead of the old two-bucket certification/graduate split. The database has carried a full 14-category/140-subcategory taxonomy with a computed freshness status per track since REQ-020/REQ-022, but nothing in the client ever read it -- `GET /api/courses` selected `st.*` alone and the home screen grouped only by `track_type`, so the list stayed flat no matter how many courses were added. `GET /api/courses` now joins each track's subcategory, category, and `view_content_freshness` status onto the row; `mobile/app/(app)/index.tsx` groups by category (favorites still pulled out on top, category count bounded at 14 so this stays scannable as courses within a category multiply, an "Other" section catches any track without a category rather than dropping it), and each course card shows the subcategory as a subtitle plus a Verified/Review due/Unverified freshness badge. `docs/education-taxonomy.md` updated to match (it still said 13 categories, predating REQ-022's Healthcare & Nursing addition) and to record where `content_format` fits. Verified with `tsc --noEmit` in both `backend/` and `mobile/`.
- REQ-035: Fixed OTA updates being offered to native builds they are not actually compatible with. mobile/app.json decided update compatibility purely by the app version string, which never changed across the 2026-09-18 Expo SDK 51 -> SDK 57 upgrade even though that upgrade changed real native code -- so a device still running the older native build could have been offered a JS update built against native APIs it does not have, and crashed. The live Play Store build had not received an update under this gap (checked -- nothing has ever been published to the production channel), but a preview build could have. Compatibility now comes from the actual native project contents instead of a version number someone has to remember to bump; needs a fresh native build before the next OTA publish so devices are running a build the new check recognizes.
- REQ-034: Fixed the actual reason the CI workspace-freshness check kept failing after REQ-033 -- the generated map itself was quietly environment-dependent. Its "Root" line named whatever folder the tool happened to run from, which differs between a developer's local clone and GitHub's own checkout, and it only read the repository's top-level .gitignore by hand, missing the separate .gitignore files backend/ and mobile/ each keep -- so a developer machine with leftover build output (an old TypeScript build cache, an exported web bundle) would commit a map a clean checkout could never reproduce. Root now comes from the repository's own git remote, and file filtering now asks git which paths are ignored instead of re-parsing just one .gitignore.
- REQ-033: Fixed the CI job that regenerates the AI-assistant workspace map so it can actually pass. `omni map` stamped a fresh generation timestamp and rewrote the file on every run, so CI's own fresh regeneration always differed from what was committed by at least that timestamp -- the check could never go green, independent of the real content drift already fixed earlier today in a separate commit. It now only rewrites the file, timestamp included, when something besides the clock actually changed.
- REQ-032: A plain "Log out" was silently turning biometric unlock back off. The same device-wipe used by "log out everywhere" and the lock screen's "use password instead" was also running on every ordinary logout, so enabling biometric unlock in Settings never actually stuck past a normal sign-out -- the next login came back with it off again, with no indication the user had changed anything. A plain logout now only ends the current session; the biometric toggle stays as the user left it.
- REQ-031: The OTA update published for REQ-029/030 had shipped with the dev machine's local network address baked in as the backend URL instead of the production one, because publishing an update reads `.env.local` (meant for local testing) the same way starting the app locally does, and that file still points at the dev machine. Every server call in that update -- logging in, Google sign-in's handoff back to our backend, anything else that talks to the server -- would have silently failed for anyone off that network. Republished with the production URL forced back in.
- REQ-030: Fixed native logins not persisting across a full app close on Android. The app's cold-start check only tried to resume a session on web; on native, with biometric unlock off, it always treated the stored login as stale and signed out, so closing and reopening the app never kept you signed in no matter what. It now resumes the same way web does, and a biometric-enrolled device still stops at the lock screen as before.
- REQ-029: Saved passwords fill in again when picking a suggested email on the login screen. REQ-027 had reverted the email field to a plain-data autofill hint as a temporary measure until Android could be shown the app and the website are the same product; that association is now confirmed live, so the field is back to the hint that pairs a suggestion with its saved password.
- REQ-028: The app now tells you when an update is ready instead of quietly applying it on some later launch. A downloaded update surfaces a prompt you can restart from, and if you have been away more than five minutes it applies on its own -- except on a lesson, PBQ or chat screen, where a reload would throw away work in progress.
- REQ-026: Fixed Google sign-in dead-ending on Android. The OAuth callback returns to a custom scheme that Expo Router tried to match as a page, so choosing an account landed the user on "Unmatched Route -- this page could not be found". The callback is now intercepted before routing, and any other unmatched route shows a real screen with a way back instead of a developer dead end.
- REQ-027: Saved email and password are offered on the login screen again. Added the Digital Asset Links file that makes that association, and restored the working hint until Google re-crawls it.

- REQ-024: Fixed login autofill so picking a suggested email also fills in its saved password. The email field's `textContentType="username"` (a credential-identifier hint) was paired with `autoComplete="email"` (a plain-data hint -- the same bucket used for shipping/contact forms), so a value tapped from that suggestion list wasn't recognized as a saved login credential and brought no password with it. Changed `autoComplete` to `"username"` on `mobile/app/(auth)/login.tsx`'s email field, matching the pairing `register.tsx` already used correctly, and added `importantForAutofill="yes"` to both the email and password fields. Widened the shared `TextField` component (`mobile/src/components/ui.tsx`) to forward `importantForAutofill`, which it previously dropped. Verified with `tsc --noEmit`; needs a manual device/simulator pass before release since this environment has neither.
- REQ-023: Fixed mobile sign-out-on-close/lock over-firing. The AppState listener in `mobile/src/auth/AuthContext.tsx` that locks a biometric-enrolled device or fully signs out everyone else treated any "background" transition as a real app close. Android has no separate "inactive" state, so the account screen's photo-library/camera picker and the Google sign-in browser tab (opened via `expo-web-browser` on both iOS and Android) also reported as "background," silently locking or signing out a signed-in user mid-task. Added a 1500ms grace period that cancels itself if the app returns to "active" first, so those in-app flows are absorbed while a genuine close or screen lock -- which lasts far longer -- still locks/signs out exactly as before; a hard OS kill mid-window is still caught by the existing cold-start session check on next launch. Verified with `tsc --noEmit`; needs a manual device/simulator pass before release since this environment has neither.
