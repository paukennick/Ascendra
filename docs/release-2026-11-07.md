New: migration `052_release_reconcile.sql`, REQ-138 (this release),
FAIL-523 to FAIL-525 (merge defects found and fixed).

**Why 027a/b/c.** The runner sorts filenames with JavaScript's default sort
(UTF-16 code units). `_` (0x5F) sorts before `a` (0x61), so
`027_legal_acceptances...` < `027a_...` < `027b_...` < `027c_...` < `028_...`.
A fresh database therefore applies B's 025-027 and then A's files in the
same order production will, so B's 026 runs before A's tables exist in both
(052 then turns RLS on for them). The CI backfill loop sorts with
`LC_ALL=C` to match; a locale-aware `sort` would put `027a` before
`027_legal` because it ignores `_`. Every reference (schema probes, tests,
records, runbooks, comments) was updated; A's REQ ranges in the runbook say
which old ids they were.

## Conflicts and how each was resolved

Each keeps both sides' behaviour; where both built the same feature there is
one data model.

1. **Legal acceptance** (A: REQ-119 `terms_acceptances`, one version string,
   a `source`; B: REQ-093 `legal_acceptances`, one row per document and
   version, already in production). One table: B's, plus A's `source`
   (052, which also moves any `terms_acceptances` rows in as a Terms and a
   Privacy row and drops that table). `lib/legal.ts` serves both client
   contracts -- `acceptedTermsVersion` and `termsVersion`+`privacyVersion` --
   at sign-up (email and Google), `/api/onboarding/terms` and
   `/api/legal/accept`, and `/api/auth/me` still returns `legalPending`.
   `CURRENT_TERMS_VERSION` is the newer of the two document versions, so a
   privacy-only change still asks everyone once. One prompt in the app: A's
   `/agree` screen (keeps the legal pages, Account and Support reachable),
   which now names which document changed and offers Sign out (B's
   `LegalAcceptGate` overlay, folded in and removed).
2. **Legal text.** B's single source `mobile/src/content/legal.ts` renders
   every page; it now also carries A's Practice labs terms (REQ-125), the
   trademark owners list (one list, `src/lib/vendor.ts`, B's marks kept), the
   AI / milestones / exam-result privacy facts (REQ-119 H3) and the
   on-device study data note. Terms and Privacy are version 2026-11-07, so
   every account (all 3 in production) is asked to agree once. FAQ and
   About: the mastery and review wording B wrote ("1, 7 and 21 days",
   "written answer reaches Independent") did not match the merged model;
   replaced with A's actual rule and the 1/3/7/21/60-day schedule.
3. **Multiple-choice grading** (A: REQ-134 server-side keys, fixed
   per-learner shuffle in `choice-order.ts`, Solo choices only through the
   hint route; B: REQ-089 shuffle on every serve, grade by chosen text). A's
   mechanism is kept (it also covers overrides, hints and replays). B's
   contract still works: `/api/grade` accepts `chosenText` when no
   `chosenIndex` is sent (exact match to one stored choice). B's per-option
   feedback is A's `*_option_reasons` (052 copies `*_choice_feedback` in and
   drops it). The practice prompt keeps B's reasoning-step and clue-check
   rules and A's item-writing rules, one reason field.
4. **Retention** (A: `purge-auth-data`, 90 days for everything; B:
   `retention`, 90 / 30 / 7 days and a whole-family guard on refresh
   tokens). One purge (`lib/retention.ts`) with B's windows -- each at or
   under A's 90 days, and they are the periods the Privacy Policy states --
   and A's transactional account-deletion purge (it also removes the
   per-device login keys). `/api/cron/retention` answers as
   `/api/cron/purge-auth-data`; `vercel.json` schedules the latter once.
5. **Account export**: A's paged export plus B's `legalAcceptances` and
   `linkedAccounts`.
6. **Report a problem**: two different things, both kept. A's per-question
   report (`item_flags`, quarantine after three reports) under each answered
   check; B's lesson-wide report (a `content_report` support ticket the
   learner can follow) at the foot of the lesson, renamed
   `ReportLessonProblem`.
7. **Try it lab step (#12) vs A's lab card**: the same `lab_prompt`. B's
   self-report is stored on A's model (`lab_objective_id`, `objective_id`
   null -- A's 035 check would otherwise reject every insert, FAIL-523) with
   format `lab`, which A's lab-report reader skips. The step follows A's lab
   rules: not offered under a plan without labs, not before a clinical or
   fitness learner has accepted the lab disclaimer, and shown with the
   disclaimer. Both appear in a lesson that has a lab prompt (see "For
   Nick").
8. **RLS** (B's 026 vs A's new tables): 052 turns RLS on for every table and
   strips anon/authenticated again, as 026 did. 026 assumes Supabase's roles;
   CI now creates them (FAIL-525).
9. **Seed**: B's "Prep for CompTIA ..." titles with A's descriptions; A's new
   Security+ V8 course follows B's rule ("Prep for CompTIA Security+ (V8)").
10. **Config**: `app.json` keeps A's plugins (expo-notifications) and B's
    `microphonePermission: false`; `vercel.json` keeps A's `npm ci`.
11. **Records**: requirement and failure ledgers unioned (B's entries
    verbatim), changelog unioned.

## Rehearsal

`backend/scripts/rehearse-production-migration.sh` (CI job "Database
(production-state rehearsal and rollback)"). Results on local Postgres 16,
2026-11-07:

- **Production state**: master @ c3e13ab's 001-024 exactly as master has
  them, B's 025-027 byte-identical to B's branch, the ledger production has
  (023-027), master's seed, then 3 accounts and 25 graded answers made
  through master's own register / login / grade routes (9 mastery rows), a
  favourite, a study session and a ticket; one cached lesson carries B's
  `fade_choice_feedback`.
- **Forward**: the baseline step records 001-022 (see the runbook: without
  it `--all` would re-run them). `--status` then listed exactly the 34 new
  files, 027a ... 053. `--all` took about 1 s. `--status`: schema current,
  every stored level matches the rule. `recompute_mastery_batched()`: 9 of 9
  pairs checked, 0 changed. Release seed, `--status` current again. 052
  moved the choice feedback into `fade_option_reasons`; 0 tables without
  RLS; 0 table grants to anon/authenticated.
- **Old code on the new schema**: master's no-AI routes (register, login,
  me, courses, course, unit, taxonomy, cached lesson, mc grading right and
  wrong, errors, attempts, study sessions, auth sessions, favourite, support
  list and create, export, health, account deletion) as a pre-release and a
  new account: 39 of 39 as expected. Nothing in the release needed changing
  for this: every new NOT NULL column has a constant default, no column was
  renamed or dropped that master reads (B's `*_choice_feedback`, dropped by
  052, was never read by master), the triggers the release adds on
  `attempts` and `mastery` accept master's writes, and master calls no
  database function.
- **Rollback**: `scripts/rollback-release-2026-11-07.sql` on the migrated
  database; `pg_dump --schema-only` then equals the production-state schema
  except three enum values Postgres cannot drop (`attempt_kind.review`,
  `attempt_kind.labtask`, `attempt_format.lab`); master's routes 39/39 again.
  Then the documented pre-deploy `pg_dump` restored over it: schema and row
  counts equal to the backup (3 accounts, 25 attempts, 9 mastery rows),
  enum values included; master's routes 39/39. Then forward again: current.
- **Fresh**: empty database, `--all`, `--status` current, seed, current; its
  schema is identical to the migrated production-state one, enum values
  included.

Master's own test suite (`lib/*.test.ts`) has no database tests, so the
route smoke (`scripts/rehearsal/master-smoke.ts`) is what exercises old code
against the database. The only change made to master's code to run it
locally: its pg pool honours `PGSSLMODE=disable` (production uses TLS).
Routes that call the model (open grading, guess feedback, chat, PBQ, lesson
generation) were not called; their writes go to the same tables.

## For Nick

1. **Try it step and lab card show the same lab.** A lesson whose objective
   has a `lab_prompt` now offers it twice: B's optional "Try it" step after
   Solo (self-report, "I did it") and A's lab card on the Done screen (with a
   graded lab report). Both are kept; they record different things. Keep
   both, keep only one, or show Try it only when there is no lab report?
2. **Lesson generation: speed vs grounding.** B made the practice half see
   the teaching text it tests (sequential calls); A runs the two halves in
   parallel for speed (wall time = the slower call, not the sum). A's
   parallel generation is kept, so B's "test what was just taught" input is
   not sent (B's other prompt rules are). Switching costs first-lesson
   latency on every new objective.
3. **Shorter retention windows.** Ended sessions are purged after 30 days
   and used tokens after 7 (B's policy text), not 90 (A's). A consequence:
   an email-change "this wasn't me" link stops working 7 days after the
   change request expires (it signed out every device; signing out
   everywhere stays available in Account).
4. **Everyone re-accepts the Terms once** (new merged version). With 3
   accounts this is a one-tap prompt; flagging because it is user-visible.
